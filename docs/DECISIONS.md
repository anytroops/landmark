# Decisions

Format: context, options, decision, consequences, date.

## D1. Go for all services (2026-10-14)
- **Context:** Need a services language for gRPC shards and coordinator.
- **Options:** Go, C++, Rust, Python.
- **Decision:** Go. Default infra language, painless gRPC (C++ gRPC builds are a time sink), fast to learn from C. Python stays for the prototype and eval.
- **Consequences:** Learning curve on Go idioms and concurrency; GC pauses become a tail-latency factor to measure.
- **Revisited 2026-10-14:** After the Python prototype worked, considered keeping fingerprinting in Python and writing only the serving path in Go (saves the port), or all Python. Kept all Go: lower end-to-end demo latency (no Python hop on uploads), a measured Go-vs-Python fingerprint speedup, cross-implementation parity as a correctness story, one toolchain. Sean prioritized end result over time.

## D2. Document partitioning by track (2026-10-14)
- **Context:** Index for fma_large (~480M postings estimated) must be split across shards.
- **Options:** Term (hash-range) partitioning; document (track) partitioning.
- **Decision:** Document partitioning, `partition = track_id mod P`. Each shard computes complete per-track offset histograms and returns only top-k. Term partitioning would ship raw postings to the coordinator and still fan out to every partition, since a query's hashes spread uniformly.
- **Consequences:** Every query fans out to all P partitions, so tail latency grows with P. Mitigate with deadlines, replica choice, hedging. Supersedes an earlier hash-range idea.

## D3. Immutable segments, mmap'd (2026-10-14)
- **Context:** Shards need fast read-only access to large posting lists.
- **Options:** Load into heap; read() on demand; mmap.
- **Decision:** Immutable segment files, mmap'd.
- **Consequences:** No locking at query time, trivial replication, OS page cache does caching. No online writes in v1.

## D4. RF = 2, no consensus (2026-10-14)
- **Context:** Need failover when a shard dies.
- **Options:** Raft-replicated index; copy immutable files.
- **Decision:** RF = 2 by copying identical immutable segments. No consensus on the read path.
- **Consequences:** Must revisit if online ingest, a mutable index, or dynamic membership is added.

## D5. Python prototype first, Go port second (2026-10-14)
- **Context:** Algorithm correctness must be validated before building infrastructure around it.
- **Options:** Go from day one; Python first.
- **Decision:** Python prototype first.
- **Consequences:** Fast iteration in Sean's strongest language, golden vectors for Go parity tests, and a measured Go-vs-Python speedup.

## D6. Commit generated protobuf code under `gen/` (2026-10-14)
- **Context:** Go code imports generated gRPC stubs.
- **Options:** Generate at build time only; commit generated code.
- **Decision:** Commit `gen/`, generated by buf with remote plugins. CI runs `make proto-check` to fail if `gen/` is stale.
- **Consequences:** `go build` and `go install` work without buf installed. Slightly noisier diffs when the proto changes.

## D7. Proto service names `ShardService` and `CoordinatorService` (2026-10-14)
- **Context:** Brief sketch named the services `Shard` and `Coordinator`. buf's STANDARD lint requires a `Service` suffix.
- **Options:** Disable the lint rule; rename.
- **Decision:** Rename. Messages and RPCs unchanged from the brief.
- **Consequences:** None beyond the names.

## D8. Colima for local Docker (2026-10-14)
- **Context:** Need Docker and compose on macOS for the local cluster.
- **Options:** Docker Desktop, OrbStack, Colima.
- **Decision:** Colima (installed via Homebrew, no GUI or license prompt), with the Homebrew docker CLI and compose plugin. VM started with 4 CPUs, 8 GB RAM.
- **Consequences:** Benchmarks on this laptop run inside a Linux VM; record that in machine specs. Start it with `colima start` after a reboot.

## D9. Peak picking: top-N per time block (2026-10-14)
- **Context:** Constellation peaks must be dense enough to match and sparse enough to keep the index small. A global amplitude floor makes density depend on loudness and genre.
- **Options:** (A) max filter + global floor; (B) max filter + adaptive local floor; (C) max filter, keep the strongest N per time block, plus a low absolute floor.
- **Decision:** C. 17x17 max filter, floor -20 dB (rejects near-silence only), 30 peaks per 43-frame (~1 s) block. Sean's pick.
- **Consequences:** Peaks/s is fixed by construction, so index size is predictable (landmarks/s ~ peaks/s x fanout). Under noise the strongest peaks survive. Block boundaries are a ranking discontinuity; a time shift that is not block-aligned can change which peaks survive near boundaries.

## D10. Pairing: nearest FANOUT in a frequency-bounded zone (2026-10-14)
- **Context:** Which later peaks each anchor pairs with determines hash specificity and robustness.
- **Options:** (A) next FANOUT, 1 <= dt <= 63, no f bound; (B) same with |f2 - f1| <= 64 bins; (C) FANOUT strongest in the zone.
- **Decision:** B. FANOUT 5, min_dt 1, max_dt 63, max_df 64. Sean's pick.
- **Consequences:** f2 is constrained near f1, so the hash's effective entropy is lower than 24 bits (~9 + 7 + 6). Watch posting-list skew for common keys. Pairing is vectorized as an (n x width) candidate matrix with a cumsum rank, no Python loop.

## D11. Prototype index: sorted arrays in segment-v1 layout (2026-10-14)
- **Context:** The brief said dict-based. Estimated (not measured) ~70 B per (track, t) tuple in Python puts fma_small at 2 GB+ RAM with pure-Python matching.
- **Options:** (A) dict of lists; (B) sorted keys + offsets + posting arrays, vectorized matching; (C) dict index + numpy matcher.
- **Decision:** B. Postings sorted by (key, track, t), structure-of-arrays. Matching: searchsorted on keys, flattened range gather, votes as unique counts over packed (track << 32 | offset + 2^31). Sean's pick.
- **Consequences:** Same layout as segment v1 minus varint encoding, so the Go port is a translation. A brute-force dict matcher is kept in tests as the correctness oracle.

## D12. Duplicate-aware eval splits (2026-10-14)
- **Context:** First full val run: no threshold met FAR <= 0.5%. Every high-scoring "negative" was a correct match to a duplicate in FMA: re-uploads, radio edits, clean versions, instrumentals, shared riddims, intro/outro pairs sharing audio. 11 of 500 val negative tracks had a copy in the index.
- **Options:** (A) dedupe by metadata (artist + normalized title); (B) dedupe by audio: index all tracks, query each full clip, union-find pairs above a score threshold; (C) leave labels and accept a noisy FAR.
- **Decision:** B. Split by cluster, not track: a cluster lands entirely in indexed, val_neg, or test_neg. Positives take one track per cluster. A positive is correct if top-1 is in its cluster. Threshold 25 on the full-clip pair score, chosen by inspecting pairs per score band (`eval/results/dup_pairs_small.csv`): >= 60 is almost all same-song versions; 40-60 includes cross-artist shared audio (riddims, instrumentals); 30-40 mostly versions; < 30 mostly coincidental. Over-clustering only moves unrelated tracks together, so err low. At 25: 150 clusters, 340 tracks, largest 10. The 2 undecodable tracks are excluded from splits.
- **Consequences:** Ground truth now depends on the fingerprinter itself, which is circular in principle: a duplicate it cannot detect stays unlabeled. Metadata (A) would miss intro/outro and cross-artist riddim cases, which this catches. Re-run dedupe whenever fingerprint params change.

## D13. Threshold calibration objective (2026-10-14)
- **Context:** The first calibration maximized mean val accuracy over all conditions with pooled FAR <= 0.5%. It picked t_abs = 2, because the speed conditions (an expected v1 failure) rewarded the loosest threshold the FAR cap allowed.
- **Options:** include all conditions; exclude speed; optimize a single anchor condition (e.g. SNR 5 dB).
- **Decision:** Exclude speed conditions from the objective; pooled val FAR <= 0.1%. Grid: t_abs 2-60, t_ratio {1, 1.25, 1.5, 2, 2.5, 3, 4}.
- **Consequences:** Result on seed 0: t_abs 12, t_ratio 2.5. Speed accuracy at threshold is reported but not optimized for. Changing the condition set changes thresholds; rerun summarize after any change.

## D14. Acceptance ratio ignores the top-1's duplicate cluster (2026-10-14)
- **Context:** Every clean positive that was correct but rejected had a duplicate in the index as runner-up (one exact 778/778 tie). The ratio test read agreement between copies as ambiguity.
- **Options:** (A) ship duplicate clusters with the index; ratio compares top-1 to the best track outside its cluster; (B) drop the ratio test, absolute threshold only; (C) accept the loss.
- **Decision:** A. Sean's pick. `Index.cluster` maps each dense id to its cluster representative; `Result.runner_up` is the best score outside the top-1's cluster.
- **Consequences:** The serving path needs cluster ids alongside the segments (Phase 2/3: store in the track metadata SQLite, not in segments). Clusters come from `eval/dedupe.py`, so ingest must run dedupe before serving. Measured (test, own val thresholds): clean 10 s 99.2 to 100.0, SNR 0 dB 93.5 to 94.5 (`summary_seed0.json` vs `summary_seed0_d14.json`).

## D15. Multi-shift query fingerprinting (2026-10-14)
- **Context:** A query starts at an arbitrary sample, so its STFT grid is offset from the track's by a fraction of a hop; peaks move by +/-1 frame or bin and hashes change.
- **Options:** (A) fingerprint the query at n sub-hop offsets (hop/n apart) and union the landmarks; (B) coarser hash quantization (drop a bit of dt and f); (C) defer.
- **Decision:** A with n = 4 (64-sample steps). Sean's pick. Index side unchanged. Exact duplicate (hash, t) pairs are dropped so nothing votes twice.
- **Consequences:** ~4x query landmarks, so more postings scanned and more search time per query: measure in Phase 4 latency benchmarks. Votes from different grids can split between offsets d and d+1; if that limits the gain, add +/-1 offset tolerance to scoring. The Go port must implement this on the query path. Measured (test, vs D14 alone): SNR 0 dB 94.5 to 95.4, SNR 5 dB 98.0 to 98.8, mean search 6.9 to 13.8 ms. Paired McNemar: same direction in every noise condition, significant only at SNR 5 dB 10 s (p = 0.02) (`compare_seed0_d14_vs_d14_shift4.md`). Calibrated thresholds moved to t_abs 30, t_ratio 1.0. Speed +/-2% raw top-1 rose 39 to 66 but accepted fell (still an expected failure). Keep for now; revisit against Phase 4 latency budgets since it is a query-side flag.

## D16. Go FFT: gonum (2026-10-14)
- **Context:** The Go fingerprinter needs a real FFT of fixed size 1024.
- **Options:** (A) gonum `dsp/fourier`, pure Go, float64; (B) hand-written fixed-size FFT; (C) FFTW via cgo.
- **Decision:** A. At float64 all three agree to ~1e-12, so accuracy is identical; the choice is speed vs build complexity. gonum keeps the build pure Go (static binaries, simple Docker). Sean asked for whichever gives the best results; this is that.
- **Consequences:** FFT sits behind a small internal function so it can be swapped if pprof shows it dominates query latency (the query path runs ~4 x 430 FFTs per 10 s clip with D15).

## D17. Exact Go/Python parity via float64 in both (2026-10-14)
- **Context:** numpy 2.x computes `rfft` of float32 input in complex64. gonum is float64. Peak picking compares values for equality (local max) and ranks by magnitude, so precision differences change which peaks win near ties.
- **Options:** (A) switch Python to float64 and regenerate golden vectors; (B) keep Python float32, accept the brief's Jaccard >= 0.98 bar.
- **Decision:** A. Sean's pick. Parity target tightened: any mismatch beyond FFT rounding is a bug.
- **Consequences:** Python spectrogram memory doubles (~5 MB per 30 s clip, irrelevant). Dedupe, splits, index, eval, and golden vectors are regenerated; accuracy change from the precision switch is measured (tag `_f64`).

## D18. Go max filter: van Herk/Gil-Werman, plain comparisons (2026-10-14)
- **Context:** First Go-vs-Python throughput run: Go was ~5x slower than numpy/scipy on one core (89 ms vs ~18 ms per 30 s clip). pprof: max filter 77% of CPU, half of that inside `math.Max`; the FFT was ~4%.
- **Options:** (A) direct separable loop (w comparisons per cell per axis); (B) van Herk/Gil-Werman sliding max (~3 per cell for any w); (C) monotonic-queue sliding max.
- **Decision:** B, with plain `>` instead of `math.Max` (values are finite, so its NaN and signed-zero handling is waste). Output is identical: the naive-2D test and exact FMA parity still pass.
- **Consequences:** 89 ms to 25 ms per 30 s clip on the M4 Pro (BenchmarkFingerprint30s). Remaining profile: spectrogram ~52% (log10 ~23%, FFT ~17%), max filter ~29%. Stopped here: ingest is decode-bound, and query-path cost is better judged against Phase 4 latency numbers. Next lever if needed: run the 4 query shifts in parallel goroutines.

## D19. Partition-local track ids in segments (2026-10-14)
- **Context:** Tracks map to partitions by `global mod P`. Varint postings store track gaps; within one partition, global ids are P apart.
- **Options:** global ids in segments; local ids (`global / P`), converted back on answer.
- **Decision:** Local. Sean's pick. Header stores partition and n_partitions; `Segment.GlobalTrack(local) = local * P + partition`.
- **Consequences:** Gaps ~P times smaller (about log2(P) fewer bits each). Changing P means rebuilding segments, which a mod-P scheme requires anyway. Size effect to be measured in B4 against a global-id build.

## D20. Key lookup: sorted keys + binary search, flag reserved (2026-10-14)
- **Context:** ~5,600 hash lookups per query (D15). At fma_large scale nearly all 2^24 possible keys exist, where a direct-addressed table (one u64 per possible key, ~134 MB) could be smaller and needs one probe instead of ~24.
- **Options:** (A) binary search over sorted keys (brief); (B) direct table; (C) both, chosen per segment.
- **Decision:** A for v1. Sean's pick. Flags bits 2-3 reserved for the lookup structure, so B can be added without a version bump; readers reject unknown values today.
- **Consequences:** Decide B with Phase 4 latency data (cold and warm page cache), not estimates.

## D21. Segment v1 implementation details (2026-10-14)
- 32-byte header (magic, version, flags, n_keys, n_tracks, n_postings, partition, n_partitions); keys padded to 8 bytes so u64 offsets are aligned; CRC-32C footer (hardware-accelerated).
- Reads go through `encoding/binary` on the mapped bytes, not `unsafe` casts to []uint32: portable, no alignment assumptions, bounds-checked. Revisit only with pprof evidence.
- `FromBytes` validates every structural invariant (checksum, sizes, strictly increasing keys, monotonic offsets spanning the blob) so lookups can index safely; the varint decoder still range-checks every posting. Fuzzed: 47.5M executions locally without a panic; CI fuzzes 20 s per run.
- Writes are atomic: temp file, fsync, rename. A crash never leaves a partial segment under the real name.
- Postings in varint segments are not fully decoded at open, so a count mismatch with the header surfaces at lookup time as ErrCorrupt.

## D22. Go matcher: sort-and-count votes (2026-10-14)
- **Context:** The matcher is the hottest code on the query path: ~350k postings per query on fma_small with 4 shifts (D15), millions at fma_large scale.
- **Options:** (A) hash map from (track, offset) to count; (B) pack votes into uint64, sort, count runs; (C) prune to top tracks by raw hit count, then build offset histograms for those only.
- **Decision:** B. Sean's pick. Buffers are reused per Matcher, so a query allocates only its result. Start with `slices.Sort` (pdqsort) and switch to radix sort only if pprof shows sorting dominates. Adjacent repeated query hashes reuse their postings (queries arrive sorted by hash).
- **Consequences:** Exact parity with prototype/match.py, tie-breaking included (best offset = smallest; equal scores rank by track id), checked in CI against 21 golden queries plus a brute-force map reference. C remains the Phase 4 lever if the matcher dominates latency; it is approximate and would need its own eval. Duplicate-aware runner-up (D14) needs top-k longer than the largest cluster (10 on fma_small); shards should return k >= 11.

## D23. Shard concurrency: fixed Matcher pool with deadline-bounded wait (2026-10-14)
- **Context:** gRPC runs each request on its own goroutine. Under overload, running every search at once shares the CPU among all of them, so every request slows down, and the coordinator's fan-out waits for the slowest shard.
- **Options:** (A) new Matcher per request (GC churn from multi-MB buffers, no overload protection); (B) pooled Matchers, unlimited concurrency; (C) fixed pool of Workers Matchers; a request waits for one until its deadline or MaxQueueWait, else is rejected.
- **Decision:** C. Sean's pick. Workers defaults to the core count, MaxQueueWait to 100 ms. Waiting past MaxQueueWait returns RESOURCE_EXHAUSTED (shed load); the caller's own deadline expiring first returns DEADLINE_EXCEEDED.
- **Consequences:** Bounded CPU contention and no per-query garbage. Phase 4 should show it: under overload, accepted-request p99 stays flat while the reject rate rises. The coordinator must treat RESOURCE_EXHAUSTED as "try the other replica". Also: graceful shutdown waits for in-flight searches before unmapping the segment (unmapping under a reader is a segfault), and skips the unmap after a forced stop.

## D24. Coordinator retries: per-attempt timeout, then the other replica (2026-10-14)
- **Context:** A crashed replica fails fast (connection reset), but a hung one (frozen, overloaded, partitioned) holds the request until the deadline, which would make its partition miss every query routed to it.
- **Options:** (A) whole budget to one attempt, retry only fast errors; (B) first attempt gets half the remaining budget when another replica exists, then the other replica gets the rest; (C) hedged requests.
- **Decision:** B. Sean's pick. Never retry INVALID_ARGUMENT (fails on every replica) or when the query's own deadline has passed. Skip attempts with under 5 ms left. Replica choice: fewest in-flight requests, random among ties.
- **Consequences:** A hung replica costs a query about half the deadline instead of its partition. Hedging (C) stays the Phase 6 stretch, to be measured against B on p99. Mutation-tested: removing the split makes the hung-replica test return partial answers.

## D25. Failure detection: health polling plus outlier ejection (2026-10-14)
- **Context:** Between health polls, traffic keeps hitting a dead replica.
- **Options:** (A) health polling only; (B) polling plus ejection after consecutive request failures.
- **Decision:** B. Sean's pick. Defaults: poll every 1 s (250 ms timeout), eject after 3 consecutive failures for at least 5 s, reinstate on a passing health check after that. RESOURCE_EXHAUSTED does not count: ejecting an overloaded replica pushes its load onto its partner and cascades. If every replica of a partition is unavailable, verified ones are still tried ("panic mode"), since health state can lag. A replica reporting NOT_SERVING (draining) gets no traffic.
- **Consequences:** Reaction to failure is milliseconds at high QPS rather than up to a poll interval. Mutation-tested: counting overload as failure ejects a merely busy replica.

## D26. Replica identity verification (2026-10-14)
- **Context:** Replication is file copying with no consensus (D4). A replica serving a stale or different segment would give different answers depending on routing, silently.
- **Options:** (A) trust the config; (B) shards report segment identity (Info RPC: partition, n_partitions, CRC-32C) and the coordinator uses only replicas matching index.json.
- **Decision:** B. Sean's pick. Verified every health round, so a replica restarted with a different file drops out within one poll. A Search response claiming the wrong partition unverifies the replica immediately. Unverified replicas are never used, not even in panic mode: a partial answer beats a wrong one.
- **Consequences:** Rolling out a new index needs a deliberate switch (new index.json and config), which is the right shape for versioned deploys later. Mutation-tested.

## D27. Radix sort for votes (2026-10-14)
- **Context:** D22 said: start with `slices.Sort`, switch to radix only if pprof shows sorting dominates. A saturated P=4 run (700 qps, `bench/results/prof_p4_small_r700_procs3`) put Matcher.Search at 76% of shard CPU, 54% in pdqsort. (A 500 qps profile instead showed mostly runtime overhead from idle spinning; below the knee, profiles overstate overhead.)
- **Options:** keep pdqsort; LSD radix sort; prune-then-count (D22 option C, approximate).
- **Decision:** LSD radix sort, one byte per pass, skipping bytes identical across all keys (computed from the OR and AND of the keys). Vote keys are track<<32 | (offset + 2^31) with small tracks and offsets, so ~3-4 of 8 bytes vary. Below 512 keys, `slices.Sort`. Output identical; golden parity and brute-force tests unchanged.
- **Consequences:** 4.3x faster on 100k realistic votes (BenchmarkSortVotes: 4.56 ms to 1.07 ms, M4 Pro). One extra reusable buffer per Matcher (8 bytes per vote). End-to-end effect measured in B1 below.

## D28. Packed request format: hashes and times as parallel arrays (2026-10-14)
- **Context:** Saturated P=4 profiles after D27 (`bench/results/prof_p4_small_r1000_radix`): the coordinator spent ~52% of CPU in network writes and ~25% in protobuf work, and shards showed GC activity (madvise, preemption) and syscalls, because every query's ~3,800 landmarks travelled as individual `Landmark` messages, re-encoded once per partition and decoded into one object each.
- **Options:** (A) `repeated fixed32 hashes` + `repeated uint32 times` (packed); (B) keep messages, tune GC; (C) one bytes field with a custom encoding.
- **Decision:** A. Sean's pick. Field 1 (`landmarks`) is reserved so the number is never reused. `fixed32` for hashes because 24-bit hash values mostly need 4 varint bytes anyway and fixed-width decodes faster; times stay varints (2 bytes typical). Mismatched array lengths are INVALID_ARGUMENT. The coordinator passes the same slices to every partition.
- **Consequences:** Requests shrink 40% (35.9 KB to 21.6 KB mean over the 1,499 replay queries; 9.4 to 5.7 bytes per landmark, `bench/results/msgsize.json`) and decode into two slices instead of ~3,800 objects. Breaking API change; every client (CLI, loadgen, Python eval backend) updated in the same commit. End-to-end effect measured in B1 below.

## D29. B2 confirms a rate by the median of its reps (2026-10-16)
- **Context:** The first B2 attempt on fma_medium required all 3 full-method reps (120 s each) to meet the SLO. Near the knee, single reps failed from short clusters of slow seconds (arrival bursts queueing near saturation, plus occasional macOS background activity) at rates where the other reps passed easily, so the step-down drifted without a floor. The brief's methodology is 3 reps reporting the median and the spread, not all-must-pass. That attempt was stopped and its results discarded, so no numbers from it are cited.
- **Options:** all reps must pass; median of reps must pass; more reps or longer runs.
- **Decision:** A rate is confirmed when the median p99 and median success across 3 reps meet the SLO (p99 <= 100 ms, success >= 99.9%); every rep's numbers are kept in result.json so the spread is visible. Bisection probes lengthened from 30 s to 60 s, since short probes were optimistic near the knee. The step-down stops at --lo.
- **Consequences:** B2 reports a typical sustainable rate rather than a worst-case one; a reader can see from the reps how often a run at that rate breached the SLO. A worst-case (all-reps) number would need a quieter machine than a laptop.

## D30. Stop list: skip query landmarks with very long posting lists, in the coordinator (2026-10-17)
- **Context:** Per-query work (postings scanned, then sorted as votes) grows linearly with catalog size at any key-space fill, about 32,000 postings per query per 1,000 tracks on fma_medium (BENCHMARKS, postings section). It is concentrated: the longest 0.1% of posting lists produce 32% of postings scanned while serving 4.2% of query landmarks, and they are mostly held-note, short-gap, and low-frequency pairs that repeat across songs, so a wider hash would not split them.
- **Options:** (A) skip hashes whose list is longer than a cutoff (a stop list, as text search does with common words); (B) change pairing so those pairs are not generated (fingerprint change, re-index, re-validate parity and accuracy); (C) change nothing and scale out. Placement for A: (1) in the coordinator using global counts, or (2) in each shard using its own partition's counts.
- **Decision:** A, placement 1. Sean's picks. `cmd/ingest` (or `cmd/stoplist` for existing indexes) writes `stoplist.lmst`: every hash with at least 0.2% of the catalog's track count in postings, with its global count, CRC-32C, recorded in index.json. The cluster config's `stop_fraction` (0 = off) drops query landmarks whose hash count exceeds `stop_fraction` x tracks before fan-out. The cutoff is a runtime setting so several can be evaluated on one index.
- **Consequences:** Every partition searches the same landmarks, so answers stay identical across partition counts (checked with `bench/equiv`); placement 2 could keep a hash in one partition and drop it in another. Requests shrink by the dropped landmarks. Measured on fma_medium P=1 (EVAL and BENCHMARKS, stop list sections): at 2% of tracks, 925 vs 550 qps under the SLO (1.7x, baseline rerun in the same session) with 44% fewer postings scanned; at 4%, 719 qps (1.3x). Clean and MP3 accuracy unchanged; SNR 0 dB accuracy 97.1% to 94.4% (2%) or 95.5% (4%), significant by exact McNemar; FAR within 0.1%. Thresholds recalibrated per cutoff (D13). Default cutoff 4% (Sean's pick, 2026-10-17): the smaller accuracy cost for a 1.3x gain. deploy/cluster.p2.json runs it with the thresholds calibrated for it (t_abs 2, t_ratio 4.0) on fma_medium, now the compose default index; the bench harness default stays off so earlier results reproduce. C still applies for growth: the stop list shrinks the constant, not the linear trend.

## D31. DJ tracklisting, matching: speed grid first, then ratio triplet hashes (2026-10-17)
- **Context:** Next feature (docs/design/dj-tracklisting.md): tracklist recorded DJ mixes. DJs change tempo by a few percent; at +/-2% turntable speed, accuracy at threshold is under 1% on fma_medium (EVAL.md) because (f1, f2, dt) hashes and constant-offset voting are not scale invariant.
- **Options:** (A) search each query at a grid of speeds with today's index; (B) Panako-style triplet hashes from ratios that survive speed changes, with voting on (track, offset, speed); (C) Qfp-style quad descriptors with range search and verification.
- **Decision:** A first as the baseline and tolerance measurement, then B. Sean's pick. C is the fallback if B cannot approach the published Qfp result.
- **Consequences:** A changes only the query side (cost x grid size; recalibrate thresholds for the extra attempts). B needs a new fingerprint with Python reference and Go parity and a new voting scheme, but keeps u32 hash lookups, the segment format, and the shard and coordinator paths. Benchmark: the Mixotic set (real DJ mixes, published baselines), downloaded with Sean's approval and to be deleted when the feature is done.

## D32. DJ tracklisting, segmentation: Viterbi over per-track alignments (2026-10-17)
- **Context:** Window-level matches must become one tracklist with start and end times, through crossfades, with an "unknown" state for unreferenced music.
- **Options:** (i) majority-vote smoothing of window results; (ii) sequence decoding (Viterbi with a switch penalty and an unknown state); (iii) per-track alignment: fit a line through each candidate's (mix time, reference time) matches, whose slope is the speed.
- **Decision:** ii + iii. Sean's pick. Alignment gives trustworthy per-track evidence (real plays advance linearly; chance matches do not) and the speed and boundaries; Viterbi turns it into one non-flickering tracklist. (i) is the baseline to beat.
- **Consequences:** Needs windowed queries with offsets kept per match; metrics are track-level precision and recall, boundary error at 5/10/20 s tolerances, and speed error, plus the published per-second protocol on Mixotic for comparison.

## D33. B2 front end: log-frequency filterbank over a 4096-sample STFT (2026-10-17)
- **Context:** D31 option B2 needs hashes that survive tempo change (turntable and keylock) while staying specific enough to search a large catalog in one lookup. The front-end experiment (`eval/frontend_experiment.py`, `eval/results/frontend_seed0.md`; 200 fma_medium test excerpts, turntable and keylock at +/-2 to 8%, noise at 10 dB) compared today's linear STFT, log filterbanks over 2048- and 4096-sample STFTs, and a constant-Q transform.
- **Options:** (a) today's STFT with frequency-gap-ratio triplets; (b) log filterbank over STFT 2048; (c) log filterbank over STFT 4096; (d) constant-Q transform.
- **Decision:** (c). Sean's pick. 36 bands per octave from 55 Hz, hop 256, the same peak density as today (30 per 43-frame block).
- **Why:** peak survival under turntable change is similar for (a), (c), and (d) (73 to 83%), lower for (b) (65 to 67%). The axis decides specificity: on a log axis a pitch shift slides all peaks equally, so a triplet hash keeps both frequency gaps exactly (16.6 bits of entropy; about 6M postings scanned per 10 s query projected at fma_medium), while on a linear axis it can keep only their ratio (11.3 bits; about 206M). Log axes also keep more peaks under noise (78 to 83% vs 67%). (c) matches (d) on stability and specificity and is an FFT plus a fixed filter matrix, so the Go port can match Python exactly as the STFT does (D17); a constant-Q port is much larger.
- **Consequences:** a new fingerprint (Python reference, then Go parity), a full re-index, and 4x larger FFTs per frame (fingerprinting cost to be measured, including ingest). Scan cost per query (about 8x today's single search before further work) is the next design target: a coarse pitch band in the hash, multi-probe lookups near quantization edges, and the stop list (D30).

## D34. Segment format v2: postings carry span and band (2026-10-17)
- **Context:** The B2 matcher (D31, D33) estimates each match's tempo factor from the triplet's span (reference span / query span) and checks pitch movement from the anchor band, so each posting must carry both. Part of the B2 design Sean approved ("store each index entry's time span and pitch").
- **Options:** (a) version 2 with a flag: two extra bytes per posting after (track, t), in both encodings; (b) a side file of spans and bands parallel to the postings; (c) fold span and band into the hash key (no per-posting data, but one key per (hash, span, band) multiplies keys and loses the span ratio).
- **Decision:** (a). The header's flag bit 4 marks postings with span and band, and such files are version 2, because a version 1 reader would silently misread the extra bytes; the reader now accepts version 1 without the flag and version 2 with it, and rejects unknown flag bits. `AppendPostings` still returns (track, t) from either version, so generic readers (the stop list) work unchanged; `AppendAuxPostings` returns all four fields. The pair matcher's hot path is untouched.
- **Consequences:** 2 bytes more per posting on triplet indexes (to be measured as bytes per posting, B4); existing pair indexes keep working byte for byte. Fuzzed (9.4M executions, version 1 and 2 seeds).

## D35. B2 query fingerprint: two filterbanks, half a band apart (2026-10-18)
- **Context:** B2 turntable scores dip periodically. A turntable change of s percent slides every peak by 36 log2(1 + s/100) bands; near a half-band shift (about every odd percent) peaks round to neighboring bands inconsistently, the band differences in the hash flip, and the true track's median score falls 4-10x. At the worst steps (-6.5%, +7%) accuracy drops to 93-95% (EVAL, "B2 half-band dips").
- **Options:** (a) dual query: also fingerprint the query on a filterbank whose centers sit half a band higher, and union the two landmark sets; (b) interp: refine peak band positions with a parabola and hash the rounded difference of refined positions (index and query); (c) keep as is.
- **Decision:** (a). Sean's pick. Measured on 1,300 tracks, 0.5% turntable steps, the thresholds from the val calibration: every turntable step at 99.3-99.7% (base: worst 93.0%), lowest per-step median true score 438 (base 96), FAR 0.06% (base 0.12%). (b) left dips of up to 98.7% and accepted 5x the negatives at the same thresholds (0.62%).
- **Consequences:** Query fingerprinting and postings scanned about double (median 13,914 landmarks and 130,335 postings per 10 s query against 7,125 and 66,160); the index and the matcher are unchanged. `fingerprint_query` (Python) and `FingerprintQuery` (Go) produce the union, sorted and deduplicated as before. Earlier B2 results (B2 vs pairs, the first B2 tracklisting run) used the single filterbank and are labeled so.
